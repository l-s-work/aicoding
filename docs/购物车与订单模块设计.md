# 购物车与订单模块设计

## 1. 核心业务表设计

为确保历史订单记录不会因为未来商品信息或地址信息的变更而受影响，我们在订单相关表中采用**快照记录**的方式，而非外键关联。

### 1.1 购物车存储策略

> **设计决策**：购物车采用**纯前端存储方案**，通过 Zustand `persist` 中间件持久化到 `localStorage`。
>
> - **优势**：刷新不丢失、多 Tab 即时同步、无需后端接口请求，完全符合轻量化原则
> - **局限**：不同设备间购物车数据无法同步（小型电商可接受）
> - **安全保底**：用户点击"去结算"时，前端重新向后端校验商品当前价格和库存，以后端数据为最终结算依据
>
> 因此**不需要后端 `cart_items` 数据库表**，购物车全部由前端 `useCartStore` (Zustand) 管理。

### 1.2 主订单表 (`orders`)

包含订单的状态流转、总金额以及下单时的收货人快照信息。

- `id`: INTEGER 主键
- `order_no`: TEXT 订单号 (生成规则：日期(8位) + 用户ID后4位 + 6位随机数；若唯一约束冲突则后端自动重试，确保 UNIQUE)
- `user_id`: INTEGER 下单用户ID
- `total_amount`: REAL 订单总金额
- `status`: TEXT 订单状态（pending → paid → shipped → completed / cancelled）
- `receiver_info`: TEXT 拍屏式地址快照（JSON 字符串，包含 receiver_name / phone / province / city / district / detail_address）
- `created_at`: TEXT 下单时间
- `updated_at`: TEXT 状态最后更新时间

> **支付流程简化**：本项目不对接真实支付网关，用户点击“确认支付”按钮后，后端直接将订单状态从 `pending` 转为 `paid`（假支付）。

### 1.3 订单明细表 (`order_items`)

记录下单当时的商品详细情况，防止商品未来改名或调价影响历史账单。

- `id`: INTEGER 主键
- `order_id`: INTEGER 关联主订单的ID
- `product_id`: INTEGER 商品ID
- `product_name`: TEXT 下单时商品名称（快照）
- `buy_price`: REAL 下单时的商品单价（快照，符合 AGENTS.md 规范）
- `quantity`: INTEGER 购买数量
- `created_at`: TEXT 创建时间

## 2. 交互与对话记录设计

在智能助手场景下，除基础交易链路外，加入与用户的对话交互。

### 2.1 AI对话记录表 (`chat_messages`)

用于存储历史聊天记录及提供上下文。

- `id`: INTEGER 主键
- `user_id`: INTEGER 用户ID
- `role`: TEXT 角色（user/assistant/system）
- `content`: TEXT 消息文本内容
- `ui_type`: TEXT 识别出的动作指令类型（如 text / product_cards / order_card）
- `payload`: TEXT (JSON) 功能数据
- `created_at`: TEXT 消息发送时间

## 3. 核心处理逻辑

1.  **AI 伴随式导购悬浮**：
    全局侧边栏或悬浮按钮，随时支持多模态（交互卡片：推荐商品带加购按钮/订单物流显示）
2.  **加入购物车与下单流转**：
    用户经过意向组合并在结单生成快照后，完成订单构建。
3.  **附带上下文注入**：
    前端随用户所处页面层级（如购物车页面/单品详情页）隐式将数据注入 prompt 内进行大模型请求，使系统能够自适应"当前购物车"进行搭配推荐。

## 4. 订单状态流转与假支付

### 4.1 状态流转图

```
pending (待支付)
   │
   ├── 用户点击"确认支付" → POST /orders/{id}/pay → paid (已支付/假支付)
   │                                                    │
   │                                                    ├── 管理员点击"发货" → shipped (已发货)
   │                                                    │                        │
   │                                                    │                        └── 系统/管理员确认 → completed (已完成)
   │                                                    │
   │                                                    └── 管理员"终止交易" → cancelled
   │
   └── 用户"取消订单" → POST /orders/{id}/cancel → cancelled (已取消，需回滚库存)
```

### 4.2 假支付接口说明

本项目不对接真实支付网关。用户在订单详情页点击"确认支付"按钮后，前端调用 `POST /orders/{id}/pay`，后端直接将状态从 `pending` 更新为 `paid`，模拟支付成功。

### 4.3 取消订单库存回滚

当 `pending` 状态的订单被取消时，需在同一事务中将已扣减的库存回加：

```python
# 遍历该订单的 order_items，逐条回加库存
for item in order_items:
    await db.execute(
        update(Product)
        .where(Product.id == item.product_id)
        .values(stock=Product.stock + item.quantity)
    )
```

## 5. 接口清单

| 方法  | 路径                          | 鉴权     | 说明                                       |
| ----- | ----------------------------- | -------- | ------------------------------------------ |
| POST  | `/orders`                     | 登录用户 | 创建订单（含库存扣减、地址快照、价格快照） |
| GET   | `/orders`                     | 登录用户 | 查询当前用户的订单列表                     |
| GET   | `/orders/{id}`                | 登录用户 | 查询订单详情（含 order_items）             |
| POST  | `/orders/{id}/pay`            | 登录用户 | 假支付：pending → paid                     |
| POST  | `/orders/{id}/cancel`         | 登录用户 | 取消订单：pending → cancelled（回滚库存）  |
| GET   | `/orders/admin/all`           | 管理员   | 管理员查看所有订单                         |
| PUT   | `/orders/admin/{id}/status`   | 管理员   | 管理员统一更新订单状态（含发货/完成/终止） |
