# 小型AI驱动电商平台产品需求文档 (PRD)

## 1. 项目概述

本项目旨在构建一个带有AI智能推荐功能的微型电商系统（前后端分离）。在满足基础的电商购物闭环（展示、加购、结算、后台发货）之上，在前台融入基于大语言模型（OpenAI）的智能客服/导购功能，以提升用户体验并促成转化。

- **技术栈选型**：C端/B端前端 (React) + 后端接口 (Python · FastAPI) + 关系型轻量级数据库 (SQLite) + AI引擎 (OpenAI API)
- **缓存层**：不引入 Redis。登录态采用 `JWT + refresh/access token 拦截表` 的轻状态方案，购物车及商品数据量小、并发低，SQLite 直读即可满足需求，保持整体轻量化方向一致。

## 2. 核心用户角色

1. **消费者 (C端用户)**：浏览商品、管理购物车、生成订单、与AI导购交互。
2. **管理员 (B端商家)**：管理商品上下架、处理客户订单、系统基础维护。

## 3. 功能需求详述 (Functional Requirements)

### 3.1 前端：C端购物体验与AI交互 (React)

- **【C-01】 账号与应用登录**
  - **登录/注册**：支持账号密码方式，密码输入要求字母数字组合，后端密文存储。注册时排查重复账号，提供找回密码机制。
- **【C-02】 商品浏览与展示**
  - **列表展示**：小型电商网格状商品列表（图文、基本参数）。
  - **详情展示**：单独页面展现商品高清图、长描述、实时库存状态。
- **【C-03】 购物车与订单结算**
  - **购物车互动**：加购操作、移除选品、修改数量步进，系统自动汇总商品总计金额。
  - **生成订单**：一键结算生成待支付流转订单，形成购物商业闭环。
- **【C-04】 AI 智能导购窗口 (核心特色)**
  - **对话交互UI**：实现类似客服的侧边栏/悬浮窗对话面板。
  - **流式输出设计**：对接后端的 Server-Sent Events (SSE) 接口，呈现毫无滞后感的“打字机”流式回答。
  - **精准商品推荐**：基于 OpenAI 技术（RAG/Function Calling），根据用户发出的自然语言（例如“推荐几款高性价比的男鞋”），调取真实系统的关联商品，向用户展示推荐商品卡片和链接。

### 3.2 后端：B端后台管理与基础支撑 (Python)

- **【B-01】 系统认证与权限防控体系**
  - **鉴权颁发**：依托 JWT 技术签署访问令牌 (Token)。
  - **越权防护**：C 端操作与 B 端后台操作互相区隔，未授权或角色越权一律拦截与提示。
- **【B-02】 商品全生命周期管理 (PIM)**
  - **运维面板**：对存量电子商务商品的分页检视和精准搜索。
  - **CRUD & 素材**：新增商品（名称、售价、库存属性等）；图片及相关文件上传支持校验（大小限制、格式如word/txt/pdf/图片限制在20m内、文件多形式去重机制，并支持大文件断点续传思路）、列表管理与删除。
- **【B-03】 订单统筹管理 (OMS)**
  - **全貌监控**：展示所有状态下的买家订单、支付汇总。
  - **流转控制**：支持由管理员干预，从“已支付”转更为“已发货”以及“终止交易”等状态。

### 3.3 具体细则补充（登录流程与菜单）

#### 3.3.1 登录流程细则（注册 / 登录 / 找回密码）

- **注册（Register）**
  - 用户可通过 `username + email + password` 注册。
  - `username` 与 `email` 必须唯一，重复时返回明确错误提示。
  - 密码规则：8-20 位，必须同时包含字母和数字。
  - 后端仅存储密码哈希，不存明文。

- **登录（Login）**
  - 支持账号密码登录，连续输错密码触发临时锁定机制（防暴力破解）。
  - 登录成功后签发 Access Token，并通过 HttpOnly Cookie 下发 Refresh Token。
  - 前端统一接入自动刷新 Access Token 机制，避免频繁跳转登录页。

- **密码找回（Forgot / Reset Password）**
  - 提供“忘记密码”入口，支持邮箱验证码方式重置密码。
  - 验证码需具备有效期和一次性使用特性。
  - 密码重置成功后，旧登录态应失效（触发重新登录）。

- **登录成功跳转规则（必须）**
  - 普通用户（C 端）登录成功后默认跳转到 C 端首页：`/`。
  - 管理员（B 端）登录成功后默认跳转到管理后台首页：`/admin/dashboard`。
  - 若用户登录前访问的是受保护页面，登录成功后可优先回跳原目标页；若无原目标页则按角色回首页。

#### 3.3.2 C 端前端菜单结构细则（用户侧）

- C 端导航菜单至少包含以下页面入口：
  - **商品列表**：`/`（支持分类筛选、关键词搜索、商品卡片浏览）。
  - **我的购物车**：`/cart`（支持数量修改、删除、价格汇总、去结算）。
  - **我的订单**：`/orders`（查看订单列表、订单状态、订单详情）。
  - **我的账号信息**：`/account`（查看/编辑基础信息、密码修改、退出登录）。

#### 3.3.3 B 端后台菜单结构细则（管理员侧）

- B 端导航菜单至少包含以下页面入口：
  - **首页 Dashboard**：`/admin/dashboard`（商品总数、在售商品数、订单总量、待处理订单等统计）。
  - **订单管理**：`/admin/orders`（订单查询、状态筛选、发货/终止等操作）。
  - **商品管理**：`/admin/products`（商品新增、编辑、上下架、库存维护）。
  - **用户管理**：`/admin/users`（用户列表、角色查看、账号状态管理）。

#### 3.3.4 验收标准（本次补充项）

- 注册、登录、找回密码三个流程可独立联调并通过。
- 登录成功跳转行为符合“按角色回首页”的规则。
- C 端菜单四项入口均可访问且路由有效。
- B 端菜单四项入口均可访问，且非管理员访问后台路由返回 403/跳转无权限页。

#### 3.3.5 商品分类与商品新建联动细则（重点补充）

- **目标**
  - 管理员在“新建商品”时，既可以选择已有分类，也可以在当前流程中新建分类。
  - 分类层级最多 3 级（一级/二级/三级），`category_code` 必须由后端自动生成，前端禁止传入。

- **前端交互要求（商品管理页）**
  - 在“新建商品”表单中提供两种入口：
  - **方式 A：选择已有分类**（级联选择器，最终选中一个叶子分类）。
  - **方式 B：新建分类后再选中**（弹窗或抽屉内完成）。
  - 新建分类时前端仅提交业务必要字段：
  - `name`：分类名称（必填）
  - `parent_id`：父分类 ID（可空；空表示一级分类）
  - 前端不提交 `category_code`、不提交 `level`，由后端计算并返回。
  - 分类创建成功后，前端应自动刷新分类树并将新分类默认选中到商品表单。

- **后端规则要求（分类创建）**
  - 后端根据 `parent_id` 判断新分类级别：
  - `parent_id = null` -> 新建一级分类（`level=1`）
  - `parent_id = 一级分类id` -> 新建二级分类（`level=2`）
  - `parent_id = 二级分类id` -> 新建三级分类（`level=3`）
  - 若 `parent_id` 指向三级分类，直接拒绝（超出最大层级，返回 400）。
  - `category_code` 生成规则由后端统一维护：
  - 一级：`01`、`02`、`03`...
  - 二级：`01-01`、`01-02`...
  - 三级：`01-01-01`、`01-01-02`...
  - 同父级下按当前最大编号递增生成，生成与写入必须在同一事务中完成。
  - 必须保留唯一性约束（`UNIQUE(category_code)`）；若并发冲突，后端自动重试一次。

- **后端规则要求（商品创建）**
  - 新建商品接口仅接受 `category_id`（最终选中的分类 ID）。
  - 后端校验 `category_id` 必须存在，且**必须为三级分类（叶子节点）**，禁止挂在一级/二级节点。
  - 商品创建流程中不允许传入或覆盖 `category_code`。

- **接口契约（PRD级）**
  - `POST /admin/categories`
  - 请求体：`{ "name": "运动鞋", "parent_id": 9 }`
  - 响应体：`{ "id": 22, "name": "运动鞋", "parent_id": 9, "level": 3, "category_code": "02-03-01" }`
  - `POST /admin/products`
  - 请求体：`{ "name": "...", "price": 19900, "stock": 30, "category_id": 22, ... }`

- **验收标准（分类联动）**
  - 前端新建分类时不传 `category_code` 仍可成功创建并返回自动生成编码。
  - 商品可在“已有分类”与“刚创建的新分类”两种路径下成功创建。
  - 任意请求若尝试创建第 4 级分类，应返回 400 且提示“最大仅支持三级分类”。
  - 并发创建同父级分类时，数据库中 `category_code` 不重复。

#### 3.3.6 分类查询与商品列表筛选细则（新增）

- **分类查询接口规则（`GET /products/categories`）**
  - 支持以下查询参数：
  - `level`：可选，1/2/3；按层级筛选分类。
  - `category_id`：可选；按指定分类查询其子分类。
  - `include_self`：可选，默认 `false`；仅在传入 `category_id` 时生效，表示是否包含当前分类节点。

- **分类查询返回规则**
  - 默认（不传参数）：返回完整分类树（一级 -> 二级 -> 三级），字段包含 `children`。
  - 传 `category_id` 且不传 `level`：返回该分类下的子分类树（`include_self=true` 时返回以当前分类为根的子树）。
  - 传 `level`：返回该层级分类列表；若同时传 `category_id`，则仅在该分类子树范围内按层级筛选。

- **商品列表筛选规则（`GET /products`）**
  - 商品列表页必须支持按**分类**与**级别**筛选：
  - `category_id`：单个分类筛选（自动包含其全部子分类商品）。
  - `category_ids`：多个分类筛选（自动包含各分类的全部子分类商品）。
  - 支持组合筛选：例如 `category_id=2&level=3`，表示“某一级分类下所有三级分类商品”。

- **验收标准（查询与筛选）**
  - 不传参数查询分类时，返回完整树形结构（含 `children` 递归字段）。
  - 传 `category_id` 可正确返回子分类数据；传不存在的分类返回 404。
  - 商品列表按 `category_id`、`category_ids`、`level` 均可筛选并分页返回。

#### 3.3.7 本轮功能补充（商品 / 订单 / 用户 / 看板）

- **商品列表筛选补充**
  - 商品列表必须支持按 `status`（`on_sale/off_sale`）筛选。
  - 商品列表必须支持按商品名称 `keyword` 模糊搜索。
  - 商品列表需支持组合筛选（分类 + 级别 + 状态 + 名称关键字）。

- **C端商品展示**
  - C端必须包含：
  - 商品列表页：`/`（支持筛选、分页、加购）。
  - 商品详情页：`/product/{id}`（展示完整信息、库存状态、加购入口）。

- **C端订单查询**
  - 我的订单列表 `GET /orders` 需支持：
  - 按订单状态筛选（`status`）。
  - 按商品名称模糊查找（`product_name`，匹配订单明细中的 `product_name`）。
  - C端必须包含订单列表页 `/orders` 与订单详情页 `/orders/{id}`。

- **管理员订单查询**
  - 管理员订单列表 `GET /orders/admin/all` 需支持：
  - 按订单状态筛选。
  - 按人名模糊查找（收货人姓名/用户名）。
  - 按商品名称模糊查找。
  - 管理员端必须支持订单详情查看与状态更新。

- **用户管理（管理员）**
  - 提供用户列表、关键字查询、状态筛选。
  - 管理员可封禁/解封用户（封禁后用户访问受保护接口应返回 403）。
  - 管理员可重置用户密码（重置后用户旧登录态失效，需要重新登录）。

- **管理员 Dashboard**
  - Dashboard 页面需展示商品维度关键统计，至少包括：
  - 商品总数、在售数、下架数、低库存数、缺货数、分类数。
  - 商品状态分布。
  - 分类商品数量 Top 列表。
  - 热门商品 Top 列表（按 hot_score）。

## 4. 非功能性需求约定

1. **安全边界**：强制应用安全的密码单向哈希策略；上传接口进行物理类型探测防漏洞。
2. **性能体验**：注重 React 层面组件复用和状态管理；AI 侧对大模型调用的流式切割渲染（FastAPI `StreamingResponse` + SSE），保障即刻感知，屏蔽长耗时。
3. **架构决策**：后端统一使用 **FastAPI**，利用其原生 async 特性及 `StreamingResponse` 低成本实现 AI 流式输出；不引入 Redis，省去额外服务的部署与运维成本。
