# 收货地址模块

## 1. 模块目标

收货地址模块负责管理用户常用地址，并在下单时为订单提供地址快照。当前模块已经实现：

- 地址新增、编辑、删除、查询
- 默认地址维护
- 地址数量上限控制
- 地址归属校验
- 下单时地址快照写入订单

## 2. 设计原则

### 2.1 地址表与订单解耦

当前项目明确采用“地址表独立管理，订单存快照”的方案：

- 地址表用于平时维护
- 下单时不保留 `address_id` 到订单
- 订单只保存 `receiver_info`

这样可以保证：

- 用户修改地址，不影响历史订单
- 用户删除地址，不影响历史订单
- 历史订单总能还原下单时的真实收货信息

### 2.2 每个用户最多 5 个地址

为了保持系统轻量和产品约束清晰，当前每个用户最多保存 5 个地址。

## 3. 数据模型

### 3.1 地址表 `user_addresses`

关键字段：

- `id`
- `user_id`
- `receiver_name`
- `phone`
- `province`
- `city`
- `district`
- `detail_address`
- `is_default`
- `created_at`

### 3.2 默认地址唯一性

数据库中通过部分唯一索引保证：

- 同一用户最多只能有一个 `is_default = 1`

索引名：

- `uq_user_default_address`

## 4. 业务规则

### 4.1 新增地址

新增地址时：

1. 查询当前用户已有地址数量
2. 如果数量 >= 5，返回错误
3. 如果是第一条地址，自动设为默认地址
4. 如果本次提交 `is_default=1`，先把其他地址取消默认

### 4.2 查询地址列表

查询当前用户地址时，按以下顺序排序：

1. 默认地址优先
2. 创建时间倒序

这样前端能优先展示默认地址和较新的地址。

### 4.3 编辑地址

编辑地址时：

- 只允许操作当前用户自己的地址
- 如果把某条地址设为默认，会先把其他地址全部取消默认

### 4.4 删除地址

删除地址时：

- 只允许删除当前用户自己的地址
- 如果删掉的是默认地址：
  - 自动把当前用户剩余地址中最新的一条设为默认
- 如果删完没有地址，则用户没有默认地址

### 4.5 设置默认地址

单独提供：

- `POST /addresses/{address_id}/set-default`

逻辑为：

1. 校验地址归属
2. 先把该用户全部地址置为非默认
3. 再将目标地址设为默认

## 5. 下单时的地址快照

订单创建时，后端会：

1. 根据 `address_id` 查询地址
2. 校验该地址属于当前用户
3. 组装地址快照：
   - `receiver_name`
   - `phone`
   - `province`
   - `city`
   - `district`
   - `detail_address`
4. 转成 JSON 字符串
5. 写入 `orders.receiver_info`

当前订单中保存的是一个大 JSON 字符串，而不是地址外键。

## 6. 前端页面设计

### 6.1 地址管理页

页面：`/addresses`

当前支持：

- 地址列表展示
- 新增地址
- 编辑地址
- 删除地址
- 设为默认

前端使用：

- Ant Design `Table`
- `Modal`
- `Form`
- `Switch`

### 6.2 结算页地址选择

页面：`/checkout`

当前逻辑：

- 进入结算页时拉取 `/addresses`
- 自动选中默认地址或第一条地址
- 支持弹窗切换其他地址
- 没有地址时提示先去地址管理新增

## 7. 接口清单

- `GET /addresses`
- `GET /addresses/{address_id}`
- `POST /addresses`
- `PUT /addresses/{address_id}`
- `DELETE /addresses/{address_id}`
- `POST /addresses/{address_id}/set-default`

## 8. 安全控制

当前地址模块的安全边界包括：

- 所有接口都要求登录
- 所有查询、编辑、删除都校验 `user_id`
- 不属于当前用户的地址统一返回不存在
- 手机号格式通过 Pydantic 和前端双重校验

## 9. 当前模块优点

- 规则清晰，符合常见电商习惯
- 默认地址逻辑完整
- 与订单快照设计天然兼容
- 前端和结算流程已经完全打通
