# 后端架构设计

## 1. 技术选型

当前后端采用轻量单体服务架构，技术栈如下：

- Python
- FastAPI
- SQLAlchemy 2.0 Async
- SQLite
- Pydantic v2
- bcrypt
- PyJWT
- OpenAI 官方 SDK
- Numpy

设计原则：

- 尽量减少外部依赖
- 单机可跑通全部业务链路
- 通过 SQLite + 事务处理核心电商场景
- AI 路由与业务计算分离

## 3. 分层设计

### 3.1 `core`

负责全局基础能力：

- `config.py`
  - 基于 Pydantic Settings 读取环境变量
  - 管理 JWT、数据库、OpenAI、CORS 等配置
- `security.py`
  - 密码哈希
  - 密码校验
  - Access Token / Refresh Token 签发
  - Token 解码

### 3.2 `db`

负责数据库连接和 ORM 模型：

- `database.py`
  - 创建异步引擎
  - 开启 SQLite WAL 模式
  - 设置 `check_same_thread=False`
  - 提供 `get_db`
  - 应用启动时执行 `init_db`
- `models.py`
  - 定义所有业务表

### 3.3 `schemas`

负责接口入参与出参校验：

- `auth_schema.py`
- `product_schema.py`
- `order_schema.py`
- `address_schema.py`
- `chat_schema.py`
- `admin_schema.py`

### 3.4 `api`

负责路由和依赖注入：

- `deps.py`
  - 获取数据库会话
  - 获取当前用户
  - 获取当前管理员
- `routers`
  - `_auth.py`
  - `_product.py`
  - `_order.py`
  - `_address.py`
  - `_ai.py`
  - `_admin.py`

### 3.5 `services`

负责复杂业务逻辑：

- `order_service.py`
  - 原子扣库存
  - 地址快照
  - 价格快照
  - 订单号生成
  - 取消订单回滚库存
- `ai_service.py`
  - 商品向量生成
  - 相似商品检索
  - AI 业务上下文拼装
  - SSE 输出内容准备

## 4. FastAPI 应用入口

`main.py` 负责：

- 创建 FastAPI 实例
- 配置应用元信息
- 配置生命周期
- 启动时自动初始化数据库
- 注册 CORS
- 注册所有路由
- 挂载 `/uploads` 静态资源目录
- 提供 `/` 和 `/health`
- 统一处理 `RequestValidationError`

## 5. 数据库架构

### 5.1 核心业务表

当前主要表包括：

- `users`
- `refresh_tokens`
- `access_token_blocklist`
- `account_recovery_requests`
- `product_categories`
- `products`
- `product_embeddings`
- `product_embedding_statuses`
- `user_addresses`
- `orders`
- `order_items`
- `chat_messages`

### 5.2 SQLite 配置

当前数据库连接具备以下特征：

- WAL 模式
- `foreign_keys=ON`
- `busy_timeout=5000`
- `synchronous=NORMAL`
- `NullPool`

这些设置使项目在小规模并发读写场景下仍然稳定。

## 6. 鉴权架构

### 6.1 Access Token

Access Token 用于接口访问，载荷中包含：

- `user_id`
- `role`
- `token_version`
- `jti`
- `type`
- `exp`

### 6.2 Refresh Token

Refresh Token：

- 通过 HttpOnly Cookie 保存
- 哈希后写入 `refresh_tokens`
- 仅用于续签 Access Token

### 6.3 鉴权依赖 `get_current_user`

校验步骤：

1. 解码 Token
2. 检查 `type=access`
3. 检查 `jti` 是否在拦截表中
4. 查询用户是否存在
5. 校验 `token_version`
6. 校验是否被封禁
7. 校验是否处于临时锁定期

### 6.4 管理员鉴权

`get_current_admin` 在 `get_current_user` 基础上增加角色校验：

- `role != admin` -> 返回 `403`

## 8. AI 架构设计

### 8.1 AI 路由与业务计算分离

当前后端不是让模型直接操作数据库，而是先在服务层完成：

- 当前页面理解
- 商品/订单/地址/账号查询
- 商品相似度计算
- 结构化卡片准备
- 追问场景判定

然后再把结构化业务快照交给模型生成自然语言。

这种设计的优点：

- 模型只负责表达，不负责查库
- 私有数据权限可控
- 易于调试和扩展

### 8.2 商品推荐

商品推荐基于两层能力：

1. Embedding + Numpy 余弦相似度
2. 关键词与文本相似度兜底

### 8.3 SSE 输出

流式对话接口使用 `StreamingResponse` 输出：

- `type=delta`：文本增量
- `type=cards`：结构化卡片
- `[DONE]`：结束标识

### 8.4 历史记录

所有用户消息和助手消息都会写入 `chat_messages`，供后续多轮对话使用。

## 9. 订单架构设计

### 9.1 地址快照

订单表中的 `receiver_info` 保存地址 JSON 快照，而不是 `address_id` 外键。

### 9.2 价格快照

订单明细表中的 `buy_price` 保存下单时价格，而不是引用商品当前价格。

### 9.3 库存扣减

在 `order_service.create_order_transaction` 中：

- 使用 `BEGIN IMMEDIATE`
- 对每个商品执行条件更新扣库存
- 任意一件失败则整体回滚

## 10. 异常处理

### 10.1 校验错误

`main.py` 中统一捕获 `RequestValidationError`，返回：

- `detail`
- `errors`

方便前端直接展示可读报错。

### 10.2 业务错误

各路由和服务层使用 `HTTPException` 返回可读错误信息，例如：

- 用户名已存在
- 库存不足
- 地址不存在
- 订单状态错误
- 权限不足

## 11. 当前架构优点

- 单体结构清晰，适合课程项目与小型业务
- API、Schema、Service、DB 分层明确
- SQLite 即可跑通核心电商业务
- AI 功能不是纯展示，而是真正与商品、订单、地址、账号打通
- 登录态、封禁、恢复申请、订单快照等关键业务都已落地

## 12. 当前可继续迭代的方向

- 增加更细粒度的日志体系

- 增加更多自动化测试和接口测试
