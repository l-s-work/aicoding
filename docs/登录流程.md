# 登录流程

## 1. 设计目标

当前项目的登录体系围绕“轻量、安全、可联动清退”设计，目标如下：

- 支持普通用户与管理员两种角色
- 支持注册、登录、忘记密码、修改密码、退出当前设备、退出全部设备
- 支持 Access Token 短期访问 + Refresh Token 无感续期
- 支持账号封禁、封禁后恢复申请、异地登录后旧会话失效
- 尽量不引入 Redis 等额外中间件，全部基于 SQLite + JWT 完成

## 2. 当前实现方案

### 2.1 Token 策略

项目采用双 Token 方案：

- Access Token：有效期 2 小时，放在前端 `localStorage` 持久化的 `auth-storage` 中
- Refresh Token：有效期 7 天，通过 `HttpOnly Cookie` 下发，前端 JavaScript 不可读取

后端在签发 Access Token 时写入以下关键字段：

- `user_id`
- `role`
- `token_version`
- `jti`
- `type=access`
- `exp`

其中：

- `token_version` 用于“退出全部设备 / 改密 / 封禁”后批量失效旧会话
- `jti` 用于“退出当前设备”后将当前 Access Token 立即拉黑

### 2.2 轻状态踢出机制

当前项目不是完全无状态 JWT，而是“JWT + SQLite 拦截表”的轻状态方案：

- `refresh_tokens`：保存 Refresh Token 的 SHA-256 哈希，用于刷新和精准删除
- `access_token_blocklist`：保存已主动失效的 Access Token `jti`
- `users.token_version`：用于全设备失效

因此系统同时支持：

- 当前设备登出立即失效
- 全部设备退出
- 管理员封禁用户后立刻 403
- 重置密码或修改密码后旧会话全部失效

## 3. 用户流程

### 3.1 注册流程

前端页面：`/register`

流程说明：

1. 用户提交 `username + email + password`
2. 后端校验：
   - 用户名长度 3-50，且只能包含字母、数字、下划线
   - 邮箱格式合法
   - 密码长度 8-20，且必须同时包含字母和数字
3. 后端检查用户名和邮箱是否已存在
4. 使用 `bcrypt` 进行密码哈希
5. 写入 `users` 表，默认角色为 `client`
6. 返回用户信息，不自动登录

### 3.2 登录流程

前端页面：`/login`

流程说明：

1. 用户提交 `username + password`
2. 后端查询用户
3. 如果账号被封禁，返回 `403`
4. 如果账号处于临时锁定期，返回 `429`
5. 校验密码失败时：
   - `failed_login_attempts + 1`
   - 连续失败 5 次后锁定 10 分钟
6. 校验成功时：
   - 清空失败计数与锁定时间
   - 兼容旧数据，将 `customer` 角色纠正为 `client`
   - 生成 Access Token
   - 生成 Refresh Token
   - Refresh Token 哈希写入 `refresh_tokens`
   - 通过 Cookie 返回 Refresh Token
7. 前端将 Access Token 和用户信息写入 `useAuthStore`
8. 按角色跳转：
   - `client` -> `/`
   - `admin` -> `/admin/dashboard`
   - 若登录前访问的是受保护页面，优先安全回跳

### 3.3 忘记密码流程

前端页面：`/forgot-password`

当前实现不是验证码方案，而是轻量重置方案：

1. 用户提交 `username + email + new_password`
2. 后端通过“用户名 + 邮箱”校验身份
3. 若命中用户：
   - 更新密码哈希
   - 清空失败计数与锁定状态
   - `token_version + 1`
   - 删除该用户全部 Refresh Token
4. 无论账户是否存在，接口都返回 `204`

这样做的目的：

- 避免通过接口探测账号是否存在
- 保持项目轻量，不引入短信或邮件服务

### 3.4 封禁账号恢复申请流程

当前登录页已经支持封禁后的恢复申请：

1. 用户登录收到“账号已被封禁”提示
2. 登录页展示“申请恢复”按钮
3. 用户填写申请原因并提交
4. 后端写入 `account_recovery_requests`
5. 管理员在后台待办页或恢复申请接口中处理
6. 管理员通过后：
   - 用户 `is_active = 1`
   - 清空失败计数与锁定状态
   - `token_version + 1`

### 3.5 修改密码流程

前端页面：`/account`

流程说明：

1. 已登录用户输入当前密码和新密码
2. 后端验证当前密码
3. 新密码不能与旧密码相同
4. 更新密码哈希
5. `token_version + 1`
6. 当前请求的 Access Token `jti` 写入拦截表
7. 删除全部 Refresh Token
8. 前端收到成功后主动退出并跳回登录页

## 4. 前端联动机制

### 4.1 `useAuthStore`

前端使用 Zustand 存储登录态：

- `token`
- `user`
- `login`
- `setUser`
- `logout`

并通过 `persist` 持久化到 `localStorage`。

### 4.2 `request.ts` 请求拦截

请求发出时：

- 自动从 `auth-storage` 读取 Access Token
- 在请求头注入 `Authorization: Bearer xxx`

响应返回时：

- `401`：自动调用 `/auth/refresh`
- 刷新成功：更新本地 Token，并重放原请求
- 刷新失败：清空本地登录态并跳转 `/login`
- `403`：若为封禁场景，则联锁清退并在登录页保留恢复申请入口

### 4.3 `PrivateRoute` 路由守卫

路由守卫分两层：

1. 本地快速校验：
   - 是否存在 Token
   - 角色是否匹配
2. 后端会话校验：
   - 访问 `/auth/me`
   - 确认 Token 未过期、未拉黑、未被踢出、账号未封禁

只有校验通过才会渲染业务路由。

## 5. 数据表设计

### 5.1 `users`

关键字段：

- `username`
- `email`
- `password_hash`
- `role`
- `token_version`
- `is_active`
- `failed_login_attempts`
- `lockout_until`

### 5.2 `refresh_tokens`

关键字段：

- `user_id`
- `token_hash`
- `expires_at`

说明：只存哈希，不存明文 Token。

### 5.3 `access_token_blocklist`

关键字段：

- `user_id`
- `jti`
- `expires_at`

说明：当前设备退出后，Access Token 立即命中拦截表。

### 5.4 `account_recovery_requests`

关键字段：

- `user_id`
- `username`
- `reason`
- `status`
- `admin_note`
- `processed_by`
- `processed_at`

- `PUT /admin/recovery-requests/{request_id}/process`

## 7. 状态码约定

- `401`：未登录、Token 失效、刷新失败
- `403`：账号被封禁、角色权限不足
- `409`：用户名或邮箱冲突、重复恢复申请
- `422`：请求参数校验失败
- `429`：登录失败次数过多，临时锁定
- `423`：已登录状态下访问受保护接口，但账号仍在锁定期

## 8. 当前实现特点与边界

### 8.1 优点

- 无需 Redis 即可实现会话失效控制
- 同时支持单设备登出和全设备踢出
- 前端已完成自动刷新和联锁清退
- 封禁与恢复申请流程完整闭环

### 8.2 当前边界

- 忘记密码暂不接入短信或邮箱验证码
- 未做第三方登录
- 未做设备管理列表
- Refresh Token 当前使用 Cookie，依赖浏览器正常携带凭证

## 9. 建议联调用例

1. 普通用户注册并登录，确认跳转到 `/`
2. 管理员登录，确认跳转到 `/admin/dashboard`
3. 连续输错密码 5 次，确认触发锁定
4. 使用 `/auth/logout` 后再次访问受保护接口，确认立即失效
5. 使用 `/auth/logout-all` 后，在其他页面请求接口，确认被联锁清退
6. 管理员封禁某用户后，该用户再次请求接口应收到 `403`
7. 被封禁用户在登录页提交恢复申请，管理员审批通过后重新登录
