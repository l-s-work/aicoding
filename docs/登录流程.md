# 登录模块详细设计

## 1. 核心问题辩论与决策

### 1.1 同一账号多地登录，如何处理？

**三种方案对比：**

| 方案                                            | 描述                                                                      | 优点                         | 缺点                                              | 适用场景           |
| ----------------------------------------------- | ------------------------------------------------------------------------- | ---------------------------- | ------------------------------------------------- | ------------------ |
| **方案A：完全放开**                             | JWT 无状态，天然支持多地                                                  | 零存储开销，实现最简单       | 账号泄露无法踢出旧设备                            | 安全要求极低的系统 |
| **方案B：强制单点**                             | 每次新登录使旧 Token 全部失效                                             | 安全性高                     | 必须每次请求查 DB 校验版本号，失去 JWT 无状态优势 | 金融/高安全系统    |
| **方案C（✅ 本项目选用）：多地允许 + 主动踢出** | 允许多设备同时在线；用户可主动"退出当前设备/所有设备"；后台Admin可封禁账号强制失效 | 体验好，安全可控，查DB次数少 | 需要维护 `token_version` 与 token 拦截表 | 小型电商           |

**方案C 实现细节：**

1. `users` 表新增字段 `token_version INTEGER DEFAULT 1`。
2. 签发 Access Token 时，将 `token_version` 与 `jti` 写入 payload：`{ user_id, role, token_version, jti, exp }`。
3. 每个受保护接口的 `get_current_user`：解码 JWT 后，校验 `token_version`，并检查 `access_token_blocklist` 是否命中当前 `jti`。
4. 用户点击"退出所有设备" → `token_version + 1` + 清理该用户全部 `refresh_tokens`。
5. 用户点击"退出当前设备" → 当前 AT 的 `jti` 写入 `access_token_blocklist`，当前 RT 从 `refresh_tokens` 删除。

### 1.2 登录过期如何处理？

**双 Token 方案 vs 单 Token 方案对比：**

|            | 单 Access Token                | 双 Token（AT + RT）                      |
| ---------- | ------------------------------ | ---------------------------------------- |
| 实现复杂度 | 低                             | 中（需要 `/auth/refresh` 接口）          |
| 过期体验   | Token 过期直接跳登录页，体验差 | 无感刷新，用户无感知                     |
| 安全性     | AT 有效期若太长则泄露风险高    | AT 短期（2h）+ RT 长期（7d），泄露窗口小 |
| 适合本项目 | ❌ 体验差或安全差（二选一）    | ✅ 推荐                                  |

**本项目结论：采用双 Token 方案**

| Token 类型         | 有效期     | 存储位置                                   | 用途              |
| ------------------ | ---------- | ------------------------------------------ | ----------------- |
| Access Token (AT)  | **2 小时** | 前端内存（Zustand store）或 `localStorage` | 每次 API 请求携带 |
| Refresh Token (RT) | **7 天**   | `HttpOnly Cookie`（安全，JS 无法读取）     | 仅用于刷新 AT     |

**过期处理流程：**

```
正常请求
  │
  ▼
Axios 拦截响应 → 收到 401?
  │ 否 → 正常返回
  │ 是
  ▼
自动调用 POST /auth/refresh（携带 HttpOnly Cookie 中的 RT）
  │
  ├── RT 有效 → 后端签发新 AT → 前端重试原请求 → 用户无感知
  │
  └── RT 过期/无效 → 清空前端状态 → 强制跳转 /login 页面
```

## 2. 完整登录流程设计

### 2.1 注册流程

```
用户提交 { username, password, email }
         │
         ▼
[后端校验]
  1. username 是否已存在 → 存在则返回 409 Conflict
  2. password 格式校验：必须同时包含字母和数字，长度 8-20 位
  3. email 格式正则校验
         │
         ▼
  bcrypt.hash(password, rounds=12) → 生成密文
         │
         ▼
  INSERT INTO users → 返回 201 Created
```

### 2.2 登录流程

```
用户提交 { username, password }
         │
         ▼
[后端处理]
  0. 检查 lockout_until：若当前时间 < lockout_until → 429 "账号已被临时锁定，请稍后再试"
  1. 查询 users WHERE username = ?（不存在也走到步骤2，防止用户名枚举攻击）
  2. bcrypt.verify(password, password_hash) → 不匹配则：
       failed_login_attempts += 1
       若 failed_login_attempts >= 5 → lockout_until = now() + 10分钟，failed_login_attempts 重置为 0
       返回 401 "账号或密码错误"
  3. 验证通过 → 重置 failed_login_attempts=0，lockout_until=NULL
  4. 生成 Access Token（含 user_id, role, token_version, jti，2h 过期）
  5. 生成 Refresh Token（含 user_id，7d 过期）
  6. SHA-256(RT明文) → INSERT INTO refresh_tokens（存哈希，不存明文）
         │
         ▼
  响应：
    - Body：{ access_token, user_info }
    - Set-Cookie：refresh_token=xxx; HttpOnly; SameSite=Strict; Max-Age=604800
```

### 2.3 找回密码流程（简化方案）

由于本项目不集成短信/邮件服务，采用**安全问题/邮箱验证码**的简化替代方案：

```
阶段一：身份验证
  用户提交注册邮箱 → 后端生成6位随机验证码 → 打印至服务端日志（开发期）
  （生产可集成 SMTP 发送邮件，但本项目范围不含）

阶段二：重置密码
  用户提交 { email, code, new_password }
  → 后端对比验证码有效性（有效期 10 分钟，存储于 SQLite password_reset_codes 表）
  → 校验通过则更新密码 + token_version + 1（踢出所有旧登录态）
```

## 3. 数据库表设计

### users 表

| 字段                  | 类型    | 约束                      | 说明                      |
| --------------------- | ------- | ------------------------- | ------------------------- |
| id                    | INTEGER | PK, AUTOINCREMENT         | 用户ID                    |
| username              | TEXT    | UNIQUE, NOT NULL          | 登录账号                  |
| password_hash         | TEXT    | NOT NULL                  | bcrypt 密文               |
| email                 | TEXT    | UNIQUE                    | 邮箱                      |
| role                  | TEXT    | DEFAULT 'client'          | 'client' 或 'admin'       |
| token_version         | INTEGER | DEFAULT 1                 | 用于踢出旧Token           |
| is_active             | INTEGER | DEFAULT 1                 | 封禁控制                  |
| created_at            | TEXT    | DEFAULT CURRENT_TIMESTAMP | 注册时间                  |
| failed_login_attempts | INTEGER | DEFAULT 0                 | 连续登录失败次数          |
| lockout_until         | TEXT    | NULL                      | 锁定截止时间，NULL=未锁定 |

### password_reset_codes 表

| 字段       | 类型    | 说明              |
| ---------- | ------- | ----------------- |
| id         | INTEGER | PK                |
| email      | TEXT    | 申请邮箱          |
| code       | TEXT    | 6位随机码         |
| expires_at | TEXT    | 过期时间          |
| used       | INTEGER | 是否已使用（0/1） |

### refresh_tokens 表

> 用于单设备精准登出。存储已签发 RT 的哈希，logout 时删除对应行，使该设备 RT 立即失效（即使 Cookie 被截获也无法续期）。

| 字段       | 类型    | 约束                      | 说明                              |
| ---------- | ------- | ------------------------- | --------------------------------- |
| id         | INTEGER | PK, AUTOINCREMENT         |                                   |
| user_id    | INTEGER | FK → users.id, NOT NULL   | 所属用户                          |
| token_hash | TEXT    | UNIQUE, NOT NULL          | RT 的 SHA-256 哈希（不存明文）    |
| expires_at | TEXT    | NOT NULL                  | 过期时间（与 RT 有效期一致，7天） |
| created_at | TEXT    | DEFAULT CURRENT_TIMESTAMP | 签发时间                          |

### access_token_blocklist 表

> 用于“当前设备退出后 Access Token 立即失效”。接口鉴权时按 `jti` 查询此表，命中即 `401`。

| 字段       | 类型    | 约束                      | 说明                        |
| ---------- | ------- | ------------------------- | --------------------------- |
| id         | INTEGER | PK, AUTOINCREMENT         |                             |
| user_id    | INTEGER | FK → users.id, NOT NULL   | 所属用户                    |
| jti        | TEXT    | UNIQUE, NOT NULL          | Access Token 的唯一标识     |
| expires_at | TEXT    | NOT NULL                  | 对应 AT 到期时间            |
| created_at | TEXT    | DEFAULT CURRENT_TIMESTAMP | 拉黑时间（用于审计/定时清理） |

## 4. 接口清单

| 方法 | 路径                    | 请求体                        | 响应                | 备注                                                       |
| ---- | ----------------------- | ----------------------------- | ------------------- | ---------------------------------------------------------- |
| POST | `/auth/register`        | `{username, password, email}` | 201 + user_info     | 无鉴权                                                     |
| POST | `/auth/login`           | `{username, password}`        | AT + Set-Cookie(RT) | 无鉴权                                                     |
| POST | `/auth/refresh`         | 无（Cookie 自动携带 RT）      | 新 AT               | 无鉴权                                                     |
| POST | `/auth/logout`          | 无                            | 204                 | 写入 AT `jti` 拦截 + 删除当前 RT + 清 Cookie（当前设备即时失效） |
| POST | `/auth/logout-all`      | 无                            | 204                 | token_version+1 + 删除全部 RT + 清 Cookie                  |
| POST | `/auth/forgot-password` | `{email}`                     | 200                 | 发送验证码                                                 |
| POST | `/auth/reset-password`  | `{email, code, new_password}` | 200                 | 重置密码                                                   |

## 5. 前端实现要点 (React)

1. **Axios 拦截器**：`request.js` 中统一在请求头注入 `Authorization: Bearer {AT}`；响应拦截器捕获 `401` 后自动调用 `/auth/refresh`，成功则重试原请求，失败则跳转 `/login`。
2. **路由守卫 `<PrivateRoute>`**：检查 `useAuthStore` 中是否有有效用户状态，未登录则 `<Navigate to="/login" />`；Admin 路由额外校验 `role === 'admin'`。
3. **AT 存储**：存放于 `useAuthStore`（Zustand，内存级），页面刷新后自动触发 `/auth/refresh` 重获 AT（利用 Cookie 中的 RT 续期）。

## 6. 安全约束清单

- [x] 密码 bcrypt 哈希，rounds ≥ 12
- [x] Refresh Token 置于 `HttpOnly Cookie`，防 XSS 读取
- [x] 密码重置验证码 10 分钟过期且一次性使用
- [x] 登录失败不透露"账号不存在"还是"密码错误"（统一返回"账号或密码错误"）
- [x] 接口级别 role 权限校验，防越权操作
- [x] 暴力破解防护：连续 5 次失败锁定账号 10 分钟，失败计数存 SQLite（`failed_login_attempts` + `lockout_until`），解锁后自动重置
- [x] 单设备精准登出：`refresh_tokens` 存 RT 哈希 + `access_token_blocklist` 存 AT `jti`，logout 后当前设备立即 401
- [x] CSRF 防护：`HttpOnly Cookie` + `SameSite=Strict` 联合覆盖（浏览器自动阻止跨站请求携带 Cookie）
