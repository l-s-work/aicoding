# 库存并发设计

## 1. 问题背景

电商系统最容易出错的环节之一就是下单扣库存。即使当前项目使用的是 SQLite，也仍然需要认真处理：

- 多用户同时购买同一商品
- 同一用户重复点击“提交订单”
- 多商品组合下单时的部分成功、部分失败问题

当前项目的目标不是极高并发秒杀，而是用最轻量的方式保证“不超卖、可回滚、逻辑清晰”。

## 2. 当前方案概览

当前后端在 `order_service.create_order_transaction` 中采用：

- `BEGIN IMMEDIATE`
- 条件更新原子扣减库存
- 整单事务提交
- 失败统一回滚

不引入 Redis 分布式锁，也不引入消息队列。

## 3. 核心并发风险

### 3.1 先查后改的风险

如果采用：

1. 先 `SELECT stock`
2. 再 `UPDATE stock`

那么在两个请求几乎同时到达时会出现竞争窗口，可能导致超卖。

### 3.2 重复提交风险

同一用户在网络卡顿时重复点按钮，也可能短时间创建多笔订单。

当前项目通过两层手段降低风险：

- 前端按钮加 Loading，避免重复点击
- 后端事务原子扣减作为最终保底

## 4. 原子扣减方案

当前扣库存的关键代码逻辑是：

```python
update(Product)
    .where(Product.id == product_id)
    .where(Product.stock >= quantity)
    .values(stock=Product.stock - quantity)
```

然后检查：

- `rowcount == 1`：扣减成功
- `rowcount == 0`：库存不足或商品不存在，事务失败

这类条件更新的意义是：

- 库存判断和库存修改在数据库层一次完成
- 不给应用层留下“查完库存后被别人抢走”的窗口

## 5. 事务流程

当前下单事务执行顺序如下：

1. `BEGIN IMMEDIATE`
2. 遍历订单商品，逐条尝试原子扣减库存
3. 如果任意商品扣减失败：
   - 查询商品获取更友好的报错信息
   - `rollback`
4. 所有商品扣减成功后：
   - 查询并校验收货地址归属
   - 计算订单总金额
   - 生成订单号
   - 写入 `orders`
   - 写入 `order_items`
5. `commit`

这保证了：

- 整张订单要么全部成功
- 要么全部失败，不会出现半单状态

## 6. 为什么使用 `BEGIN IMMEDIATE`

当前项目在事务开始时显式执行：

```sql
BEGIN IMMEDIATE
```

目的：

- 立即申请写锁
- 避免多个写事务在应用层交叉推进
- 降低库存写入竞争的不确定性

对于 SQLite 这种单文件数据库来说，这是当前项目规模下简单且有效的做法。

## 7. 多商品订单的一致性

用户一次下单可能包含多个商品。当前实现要求：

- 只要其中一件商品库存不足
- 整单都失败
- 已扣减的商品库存全部回滚

这样做的好处是：

- 避免“下单成功但少买一部分”的复杂体验
- 保持订单金额、明细、库存状态一致

## 8. 取消订单回滚库存

当前取消订单逻辑位于 `cancel_order_transaction`，会：

1. 再次开启 `BEGIN IMMEDIATE`
2. 读取当前订单所有 `order_items`
3. 将每件商品库存加回去
4. 更新订单状态为 `cancelled`
5. 提交事务

当前允许取消的状态为：

- `pending`
- `paid`

实际项目中的常见路径是：

- 下单完成后订单直接记为 `paid`
- 只要未发货，仍允许取消并回滚库存

## 9. 前端防重复提交设计

### 9.1 购物车与结算页

前端在结算页提交订单时：

- 使用 `creatingOrder` 控制按钮 Loading
- 弹出二次确认弹窗
- 成功后跳转到订单详情页

### 9.2 作用边界

前端防重只能降低重复点击概率，不能替代后端事务控制。真正防超卖的关键仍然是后端的原子更新和事务回滚。

## 10. 当前方案的优点

- 无需 Redis
- 逻辑简单
- 与 SQLite 天然匹配
- 易于调试
- 对课程项目和小型电商场景已经足够可靠

## 11. 当前方案的边界

### 11.1 没有做请求幂等键

当前项目没有实现“同一提交请求只认一次”的幂等键机制，因此：

- 连续重复下单仍可能生成多笔订单
- 只是由于库存扣减和按钮 Loading，不容易出现超卖

### 11.2 不适合大促级并发

SQLite + 单机事务适合：

- 课程项目
- 小型业务
- 单机部署

不适合：

- 秒杀
- 超高并发分布式订单系统

## 12. 当前实现结论

对于当前项目规模，下面这套组合已经能较好解决库存并发问题：

- SQLite WAL 模式
- `BEGIN IMMEDIATE`
- 条件更新原子扣减
- 整单事务提交
- 取消订单回滚库存
- 前端按钮 Loading 防重复点击

这也是本项目“轻量优先、拒绝过度工程化”的实现选择。
